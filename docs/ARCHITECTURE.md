# Архитектура

## Общая схема

```
браузер ──HTTP──► eduquery (Rust, axum) ──HTTP 127.0.0.1──► llama-server (llama.cpp)
                        │                                         │
                        ├── SQLite (EDUQUERY_DATA_DIR/eduquery.db) │
                        ├── модели (*.gguf, *.gguf.part)           │
                        └── движок (llama-server) ─────────────────┘
```

eduquery — единственный процесс, который запускает администратор. При установке движка из UI он
скачивает готовую сборку llama.cpp, запускает `llama-server` дочерним процессом на localhost со
случайным портом и общается с ним по OpenAI-совместимому API. Модель загружается при первом
запросе; смена модели, контекста или параметров перезапускает сервер.

## Слои

| Слой | Файлы | Ответственность |
|---|---|---|
| Запуск | `main.rs`, `config.rs` | переменные окружения, каталоги, БД, восстановление модели, роутер |
| HTTP | `server.rs` | маршруты, авторизация, права, обработчики, keep-alive |
| Бизнес-логика | `students.rs`, `analysis.rs`, `bench.rs` | данные учеников, промпты, сравнение моделей |
| Инференс | `llm.rs` | установка и жизненный цикл `llama-server`, генерация |
| Модели | `models.rs` | каталог, зеркала, скачивание, проверка, активация |
| Хранение | `db.rs` | схема, миграции, настройки |
| Пользователи | `users.rs`, `auth.rs` | учётные записи, роли, права, сессии, лимиты |
| Экспорт | `admin_api.rs` | CSV, шаблон импорта, установка движка |
| Демо | `seed.rs` | вымышленные ученики и активности |
| Интерфейс | `web/` | HTML, CSS, классический JavaScript без сборщика |

## Запуск

1. Читается конфигурация (`EDUQUERY_*`, аргументы командной строки).
2. Создаются каталоги данных, открывается SQLite, выполняются миграции.
3. `ModelStore::reconcile` сверяет файлы `*.gguf` на диске с таблицей `models`.
4. `restore_active_model` возвращает сохранённую активную модель или назначает первую найденную.
5. Создаётся первый администратор, восстанавливаются сессии.
6. Поднимается axum-сервер; статика отдаётся из `web/`, API — из `/api/v1`.

Незавершённые бенчмарки при старте помечаются ошибкой «прервано перезапуском сервера»: после
рестарта процесс-генератор уже не существует, и вечно «выполняющийся» запуск вводил бы в заблуждение.

## HTTP и права

- Токен сессии передаётся cookie или заголовком `Authorization: Bearer …`.
- `required_perm(метод, путь)` определяет, какое право нужно. Чтение каталога, моделей, параметров и
  бенчмарков доступно любому авторизованному; изменения требуют `models`.
- `GET /health` и статика публичны.
- Ответы об ошибках — `{"error": "..."}` с кодом 400/401/403/404/409/429/500.
- Долгие запросы к ИИ отвечают `200` и шлют пробелы-«пульс» каждые 10 секунд, чтобы прокси не
  обрывали соединение по таймауту. Ошибка генерации приходит в теле как `{"error": "..."}`.

## Поток анализа

```
запрос → resolve_model_path → merged_params → build_messages
       → engine.generate → запись в usage_metrics → (для ученика) INSERT analyses → ответ
```

`build_messages` собирает:

1. системную инструкцию (`req.system` → `params.system_prompt` → `DEFAULT_SYSTEM_PROMPT`);
2. необязательную пару «пример запроса → пример ответа» (`example_input`, `example_answer`);
3. реальные сообщения пользователя.

Для характеристики используется отдельный `build_characteristic_prompt`, а не промпт разбора.

## Бенчмарки

- `POST /api/v1/benchmarks` создаёт запуск и строки результатов, затем запускает фоновую задачу.
- Генерация идёт последовательно по выбранным установленным моделям.
- По каждой модели сохраняются ответ, ошибка, токены, скорость, время и флаг зацикливания.
- `BenchState` хранит id выполняющегося запуска; второй одновременный запуск отклоняется (`409`).
- Ручная оценка 1–5 хранится в `benchmark_results.rating`; `0` — сброс.
- Все генерации пишут метрики в `usage_metrics`, поэтому вкладка показывает и реальное использование
  моделей вне бенчмарков.

## Интерфейс

`web/index.html` содержит все экраны; `app.js` переключает вкладки, ходит в API и рисует таблицы;
`stats.js` отвечает за графики и дополнительные блоки карточки ученика. Состояние вкладок и
выбранные фильтры живут в памяти страницы. Каталог моделей кэшируется в `localStorage`, чтобы список
не пропадал при недоступной сети или до завершения входа.

## Ограничения

- Один экземпляр приложения на каталог данных: SQLite и `llama-server` не рассчитаны на несколько
  параллельных процессов.
- Одновременно выполняется только один бенчмарк и одна загрузка модели с одним id.
- Контекст ограничен `n_ctx`; очень длинные отчёты обрезаются.
- Слабые модели могут зацикливаться; генерация прерывается и помечается `loop_detected`.
